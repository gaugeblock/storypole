# GB-316 — Repository identity for tickets and receipts

## Problem

A ticket does not know which repository it belongs to, so verification has to guess, and the guess is
invisible. Three costs were observed in a single session.

1. `GB-272`, `GB-273`, `GB-275` and `GB-276` were member-repository work. Their receipts named
   `feat/gb-305-multi-repo-gate` and `[1 commit(s)]` — a branch and a commit count belonging to the
   harness repository, chosen because that is where the command happened to be run.
2. Four multi-repository tests sit behind a gate whose whole purpose is proof that a mechanism works
   across repositories. The evidence could not be attributed to a repository.
3. `storypole verify` inside `miter/` reports `Task not found`. The member repository holds a stub
   store (`.gitignore` and an empty `index.sqlite`), so work cannot be verified from the place it
   happens without leaving the repository first.

## What already exists

The mechanism is present and never filled in.

| Piece | Where | State |
|:--|:--|:--|
| `TaskScope.repo`, `TaskScope.crate_name` | `gaugeblock-contracts` | exist, unset on every ticket observed |
| `resolve_target_dir` | `storypole-core::ops::verification::target` | resolves repo, then crate prefix, then **silently falls back to the harness root** |
| Per-repository chains | `.gaugeblock/config.toml` | 12 member entries plus `gaugeblock` and `default` |
| `--repo` on `add`, `list`, `next` | `storypole-cli` | a filter and a scope setter; absent on `claim` and `verify` |
| Canonical ledger | `./.gaugeblock/storypole/ledger.jsonl` | one for the suite; member repositories hold stubs |

## Decision

Resolution order, in one function, used wherever a repository is needed:

1. `--repo` argument (CLI and MCP)
2. persisted `task.scope.repo`
3. derived from the `files` and `symbols` the ticket names, through suite topology
4. derived from the working directory at claim time
5. harness — **recorded as harness, never inferred by omission**

The function returns the value *and how it was obtained*, so every consumer can say which it used.

**Invariants.**

- *A guessed value must be recorded and visible; an absent value must not resolve to a default.*
  An unscoped ticket is not a harness ticket, it is an unscoped ticket, and the receipt says so.
- *Guess once.* The derivation is persisted at claim in the same event that records the branch.
  `verify` reads it; it does not re-derive. A disagreement is an error, because the tree moved under
  the ticket and one of the two is wrong.
- *A receipt says what it covered.* `repo`, `branch`, `base`, `head`, commit count and the **chain key**
  that matched. Two receipts produced by different commands must not read the same.

## Branch policy this settles

Code branches in the member repository and fast-forwards to its `main`. The ledger stays linear on the
harness `main` as `chore(storypole):` commits, made after the member branch lands. A record on an
unmerged branch is not a record: if the branch is abandoned, the receipt disappears and the ticket
reads as never verified.

The mirror-branching (harness branched to the same name as the member branch) that agents have been
doing is a **workaround for missing provenance**, not a preference. It exists because the only way to
tie a ledger line to a code branch was to name them alike. Once a receipt carries the repository and
commit range, the mirror branch has no purpose and should not be created.

## Why this was overlooked (recorded after the fact)

The gap was not in `storypole` alone. The suite topology work answered a *downward* question — "given a
suite root, where does a tool keep its state" — and nothing needed the *upward* one, "which suite
contains this member", until a ticket asked a member repository to read the suite's backlog.

Three reasons it survived:

1. **The shared crate cannot express the question.** `GaugeblockPaths::discover` resolves through git's
   own repository discovery, so from inside a member it returns that member as a suite of one;
   `WorkspaceTopology::discover` takes the suite root as an argument. Neither can say "this repository
   is member X of suite Y". Filed as `GB-317`.
2. **The gate is dependency-shaped.** `miter audit --paths` asserts that a crate naming `.gaugeblock`
   *depends on* `gaugeblock-workspace`. `storypole-core` does — so the gate was green while the store
   ran its own ancestor walk and its own boundary test. A dependency is not a usage. Filed as `GB-318`.
3. **The `GB-305` guard was written from the symptom.** It compares two answers that are equal by
   construction inside a member repo, so it cannot fire there; and its doc comment justified local
   policy by a real constraint (stores must work in scratch directories that are not git repositories).
   A true constraint licensed a false conclusion.

Step `ledger-from-anywhere` therefore depends on `GB-317` in `common`: the topology crate gains an
upward membership resolution *and* `storypole` uses it, instead of both crates keeping half an answer.

Two related observations, not fixed here:

- A member repository's `.gaugeblock/storypole/` stub (`.gitignore` and an empty `index.sqlite`, no
  ledger) is treated as a store by `find_enclosing_store`, which is why the failure surfaced as
  `Task not found` rather than as an uninitialized store. A store without a ledger is not a store.
- `GB-311` (writes bypassing the store's discovery) is the same divergence from the other side.

## Steps

| id | step | gate |
|:--|:--|:--|
| `scope-resolution` | One resolver returning value plus provenance; wired into add/claim/verify/handoff | `cargo nextest run -p storypole-core --lib scope` |
| `persist-at-claim` | Claim persists a derived scope beside the branch it already records | claim test asserts the persisted field |
| `receipt-provenance` | Receipt records repo, branch, base..head, chain key | two receipts, different chains, must differ |
| `refuse-wrong-tree` | Member-repo ticket with no scope cannot be certified; error names the candidate | reversion-proven |
| `ledger-from-anywhere` | Canonical ledger discovered from inside a member repo; `GB-305` guard retained for non-members | reversion-proven, run from `miter/` |
| `docs` | ADR 0007, SPEC and ARCHITECTURE updates | `chalkline docs check -d storypole` |

## Out of scope

- Automatic commit-message or trailer generation from receipts.
- Cross-repository commits in a single ticket. A ticket belongs to one repository; an epic spanning
  two is a set of tasks.
